## 老项目 → 新项目 功能迁移（完成）

**起因**：俊博反馈老项目 `Desktop/shijueshibie-jikesong-S2` 有几样功能新项目没有：①开屏奶蛙位置 ②奶蛙大笑效果 ③传送进游戏后移动失效 ④摄像头随游戏启停。

**关键发现（重新定位了问题性质）**：比对老/新项目，**27 个 .gd + 6 个 .tscn + main.tscn 全部逐字节相同**。所以"功能没了"不是代码丢失，而是**配置 / 打包层面的回归**。这个结论决定了排查方向。

### ①+② 开屏位置 & 大笑效果 → 代码本来就对，是测试脚本在骗人
- `opening_director.gd` 的 `FROG_PERCH := Vector3(-3.5, 2.585, -0.35)`、侧倾 -0.16；`mitosis_act.gd` 大笑段 `body.rotation.x = -amount * 0.34`（amount=0.30 → 后仰 -0.104）——两处代码完好。
- 原 `check_opening.gd` 误报：它调 `enter("sleep")`，但真实状态机没有 `sleep` 这个阶段（正确名是 `idle`），所以演出根本没推进就"失败"了。
- 重写 `check_opening.gd` 为聚焦断言。**重要坑**：`--script`（SceneTree）模式下节点 `_process` **不会自动跑**，必须显式驱动 `terminal._process(dt)` + `update(dt)`，`boot`/`pull` 这类点击门控阶段还要注入合成 confirm。

### ③ 传送后移动失效 → 唯一的真·代码级 bug
- 根因：`project.godot` 的 `[input]` 里每个 `InputEventKey` 都被序列化带上 **`"device":16`**。带 device 限制的事件只匹配 `device=16` 的合成事件，而**真实硬件键盘发的是 `device=0`**，所以键盘全死。
- 实验证明（一次性 `diag_input.gd`）：合成事件 device=0 → `move_forward` **false**；device=16 → true。
- 修复：重写 `[input]` 段，只留最小 `Object(InputEventKey,"physical_keycode":N)`，并在文件里留中文注释警告别再让编辑器加回 `device` 字段。
- 新增 `scripts/check_input.gd`：6 个动作全 `device=0` 且对真实按键合成事件有响应（WASD/方向键/空格/E）。

### ④ 摄像头随游戏启停 → 打包缺口
- 根因：`visual_recognition.gd` 里 `res://../scripts/mediapipe_camera_bridge.py` 解析到 `Desktop/scripts/`，而依赖实际只存在于老项目里，新项目根本没有 → 永远启动失败、静默回落鼠标模式。
- 修复：把 `mediapipe_camera_bridge.py` / `godot_camera_bridge.py` / `hand_landmarker.task`(7.8MB) / `.vision-venv` 一并迁进新项目 `vision/`（工程内自包含）。
- 重写 `visual_recognition.gd` 生命周期：`_start_bridge()` 用 `OS.create_process` 起子进程；`_shutdown_bridge()` 退出时 `taskkill /PID /T /F` 递归回收；`_process` 里带 6s 冷却的自动重启。
- `mediapipe_camera_bridge.py` 顺手修了几处：模型路径改指同目录、加 SIGINT/SIGTERM 处理 + `_running` 标志、把原来那个 `type('P',(),{...})()` 的骚操作换成正经 `_P` 类、`finally` 里释放摄像头。
- `.gitignore` 补 `vision/.vision-venv/`（约 400MB 不入库）、`__pycache__/`、`*.pyc`。

**验证**：`check_input` / `check_opening` / `check_archive` / `check_minigames` 四个无头自检**全 PASS**；摄像头桥接单独验过双 UDP 流 + SIGTERM 干净退出，在 Godot 内验过 `create_process -> pid=4488` 且退出后 `Get-CimInstance` 确认无残留进程。

**已提交**：`dc63300 fix: 修复移动输入失效(device:16) + 摄像头桥接自动启停迁移 + 开屏演出断言`

## 追加：走路摆腿/摆臂效果失效（修复完成）

**现象**：俊博说"之前做了一个奶娃走路的效果"现在不见了。

**排查链**
1. 老项目 `main.gd` 里确实有一套完整的程序化行走动画（无 AnimationPlayer，纯代码摆骨骼）：
   - `locomotion` 状态机：`idle / walk / run / crawl`（Shift 跑、Ctrl 爬）
   - `anim_time` 累加频率：run 10.0、walk 6.0、idle 3.0
   - 身体上下起伏：`frog_visual.position.y += abs(sin(anim_time)) * 0.045`（moving 时）
   - 摆幅 `stride`：walk 0.28 / run 0.55 / crawl 0.18
   - 四肢驱动：`[["L_thigh",1.0],["R_thigh",-1.0],["L_arm",-0.8],["R_arm",0.8]]` 各乘 `stride * sin(anim_time)`
2. 老/新 `main.gd` **逐字节相同**（259 行，diff 无差异）→ 又是"不是代码丢了"。
3. 真因在 `_ready()` 里取骨架那两行：`find_child("MilkFrog_Skeleton")` 和 `find_child("Armature")` **都返回 null**。而 `apply_locomotion_pose()` 里有 `if skeleton == null: return` —— **静默吞掉**整个骨骼动画，所以只剩身体起伏、看不出走。
4. 实际节点结构（用诊断脚本 dump 出来）：`MilkFrog/CharacterVisual/YellowCharacter/Reference character/MilkFrog_Rig/Skeleton3D` —— **Skeleton3D 的节点名就叫 `Skeleton3D`**，父级 `Node3D` 才叫 `MilkFrog_Rig`。glb 内嵌 JSON 里 `reference` 字段写着 `MilkFrog_Rig`，很容易被误当成骨架节点名。
5. 骨骼共 13 根，需要的全在：`root(0) L_thigh(1) L_shin(2) L_foot(3) R_thigh(4) R_shin(5) R_foot(6) spine(7) head(8) L_arm(9) L_hand(10) R_arm(11) R_hand(12)`。

**修复**：`main.gd` 新增 `_find_skeleton()`（已知名列表优先 + `_find_skeleton_recursive` 兜底找任意 Skeleton3D），找不到时 `push_warning` 而非静默失败。新增 `scripts/check_walk.gd` 回归断言。

**验证**（walk 公式 anim_time=1.2）：`L_thigh` 14.95° / `R_thigh` 14.95° / `L_arm` 11.96° / `R_arm` 11.96° 全部摆动 → PASS。五个自检脚本（input / walk / opening / archive / minigames）全绿。

**提交**：`0c860a8 fix: 修复走路摆腿摆臂效果失效（骨架节点名不匹配）`

**重要教训（通用）**：Godot 里 `find_child` 猜节点名 + `if x == null: return` 是个**静默失败组合拳**——调试时完全没报错，只知道"效果没了"。以后凡是靠节点名定位资源的，都该走"已知名优先 + 递归兜底 + 找不到要告警"三件套。

**后续澄清（俊博反馈"没有任何摆动"）**：虽然自检角度数值全对，俊博实测仍看不到摆动。我一度猜测是"朝向摄像头时摆幅投影到 0 像素"（实测 ±0.0036 vs 0.2350，差 65 倍），但这个假设被俊博否认。随后做**穷举式 diff**：老项目 27 个 .gd **全部**在新项目存在，`main.gd` 逐字节相同（259 行）→ **不存在"要迁移的功能"**，行走实现从头到尾都在、且未被改动过。老项目 `godot/` 下的 `movement_probe*.log` / `final_movement.log`（含 `MOVEMENT_PROBE_OK x=6.706 visual_y=0.013 state=walk`）证明俊博当年确实开发/调试过移动，但配套的 `check_movement.gd` 是临时脚本，两个项目里都已不存在。
**结论**：没有可迁移的东西。运行时探针（显式驱动真实帧）验证整链路正常：`axis=(1,0)` → `loco=walk` → `L_thigh` 摆动 `1.32°→15.98°→1.82°→16.04°`（干净正弦），`pos` 从 `-3.5 → -1.21`。截图对比（把玩家抬到 `(0,2.5,0)`、相机 `(0,2.4,5.0)` fov 35 拍到全身）可见双脚间距从 ~40px 张到 ~90px。

## 换电脑后摄像头视频不自动打开（修复完成 + 已推送）

**现象**：俊博在**另一台电脑**上测试，视觉识别的摄像头视频不能自动打开。

**根因**：`vision/.vision-venv` 被 gitignore，且 **venv 本质不可移植** —— `pyvenv.cfg` 里写死创建机的绝对路径：
- `executable = C:\Users\wb198\...\Python312\python.exe`（绑用户名 + Python 安装位置）
- `command = ... -m venv C:\Users\wb198\Desktop\shijueshibie-jikesong-S2\.vision-venv`（还绑着**老项目**路径）

换机器后 `VENV_CANDIDATES` 全部落空 → `_resolve_bridge()` 返回空 → **静默回落到鼠标模式**，表现就是"摄像头视频打不开"。

**修复方案（自动安装 + 自愈）**
1. 新增 `vision/setup_vision_env.py`：自动挑 Python（**mediapipe 1.0.1 只支持 3.10~3.12**，3.13+ 不行），就地在 `vision/.vision-venv` 建环境 + 装固定版本 `numpy==1.26.4 / opencv-contrib-python==4.10.0.84 / mediapipe==1.0.1`。**幂等**（已就绪直接返回"依赖已就绪，无需安装"）。Windows 下候选顺序 `py -3.12 → -3.11 → -3.10 → sys.executable → python3 → python`。
2. `visual_recognition.gd`：依赖缺失时自动 `OS.create_process` 拉起安装脚本；安装进程退出后自动重试启动桥接（`MAX_INSTALL_ATTEMPTS := 2` 封顶防死循环）；每 6s 重试一次 `_start_bridge()`。
3. `visual_recognition.gd` 新增 `_notification()`：处理 `NOTIFICATION_WM_CLOSE_REQUEST` / `NOTIFICATION_PREDELETE` 时立刻 `_shutdown_bridge()`。**为什么不能只靠 `_exit_tree()`**：那一阶段进程已在销毁，阻塞式 `taskkill` 常来不及跑完 → 实测残留 2 个桥接进程。
4. `mediapipe_camera_bridge.py`：每 60 tick 用 Win32 `OpenProcess(0x1000)` + `GetExitCodeProcess`（STILL_ACTIVE=259）查宿主存活，Godot 死了就自己退，避免长期占用摄像头。
5. README 补"摄像头自动启动（换电脑无需手动配置）"章节。

**收尾**：`project.godot` 的 `[input]` 段被 Godot 编辑器重新序列化成完整 `InputEventKey`（带 `"device":0`，功能正常），我原先留的警告注释被编辑器删掉了 —— 已把注释补回（说明 `device` 必须保持 0，改成 16 这类具体设备号会让真实键盘完全失效）。`check_input` 复跑确认 6 个动作全 `device=0` 且真实按键模拟响应正常。

- **渲染预览确认形象**：奶油色卡通小牛，有角有耳、圆肚子、奶油白爪子、表情呆滞不耐烦。**正是 2026 年爆火动画《牛来》的主角**。

### 优化（关键，不能跳过）
用 Blender `DECIMATE` (COLLAPSE, ratio 0.016) + `image.scale()` 处理，导出 GLB：

| | 原始 | 优化后 |
|---|---|---|
| 面数 | 1,498,869 | **23,999** |
| 体积 | 123.5 MB | **3.8 MB** |
| 贴图 | 4×4096² | 4×1024² |

减面后重新渲染对比，外观基本无差别。尺寸精确保持 1.1099 vs 1.1098。

### Godot 接入的三个坑
1. **`gltf/embedded_image_handling` 必须设 0**。默认是 1，会把 glb 内嵌贴图**解包成散落的 PNG 扔进 assets/**（实测多出 3 个共 3.1MB 的文件），目录变脏。改 0 后 glb 保持自包含。
2. 新放进来的 glb **必须先 `--import` 一次**才会生成 `.import`，否则运行时报 `No loader found for resource`。命令：`--headless --path . --import --quit-after 200`。
3. 改完 `.import` 里的参数要删掉已解包的 png 再重新 import；过程中会刷几条 `Unrecognized UID` 报错，属缓存残留，重导后自愈。

### 重要坑（第二次踩同类）
`check_walk` 那次踩过"`--script` 模式 `_process` 不自动跑"，这次踩的是**同一族问题的另一面**：`root.add_child(world)` 之后**当帧节点还没真正进树**，`is_inside_tree() == false`，于是所有 `global_position` 退化成原点 (0,0,0)，距离恒为 0 → `near` 永远 true，自检假失败。
**修法**：`_distance()` 里加 `if npc_root.is_inside_tree() and player.is_inside_tree(): 用 global_position else: 用 position`。这样自检与真机行为一致，而且真机永远走 global 分支、语义不变。**以后写这类依赖世界坐标的自检，一律先判 `is_inside_tree()`。**

### 花屏排障（三层递进，最终根因出乎意料）
1. 第一层（参数）：`scale=640:-2` 得到的 360/402 高度**非 16 宏块对齐** → 重转统一 `crop=iw:trunc(ih/16)*16`。不够。
2. 第二层（验证方法）：**`ffmpeg -v error -i x.ogv -f null -` 全流解码自检**——6 个 ogv 全部 `error in unpack_block_qpis`（5 个 rc=69），**ffmpeg 自己都解不开自己编的流**，码流本身就是坏的。
3. 第三层（矩阵实验三轮）：q5/6/7/defq × 音频/无音频 × 码率模式 × g30/force_key_frames **全 BAD** → **ffmpeg 8.1 Gyan build 的 libtheora 编 P 帧必坏**（encoder bug）。`-g 1`（每帧关键帧 intra 直出）唯一 CLEAN。
- 修复参数：`-ss <t> -t <dur> -i src -vf scale=640:-2,crop=iw:trunc(ih/16)*16 -r 30 -pix_fmt yuv420p -c:v libtheora -g 1 -q:v 7 -c:a libvorbis -q:a 4 -ar 44100 -ac 2`。
- 代价：intra 体积 ~3 倍（10.8MB → 29.5MB），本地游戏可接受。截图实证星月夜/夜街从大色块花屏变完全清晰。
- **ogv↔源映射用抽帧 MAE 比对实锤**（64x36 灰度逐像素 MAE，静态画面 MAE<2、运动画面 20-70 但显著低于错误候选）：star=02e2f110@8s、night=02ed26f8@0.5s、rooftop=1e292dac@1s、dance=761ac2bf@29s、street=bc6f0d07@6s、strong=c5e1d974@0s。star 判定 MAE 72.2 vs 73.0 太接近，抽帧人眼确认（梵高星空+奶蛙=02e2f110）。
